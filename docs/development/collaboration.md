# 협업 규칙

`CLAUDE.md`의 원본. 규칙을 바꾸면 이 문서를 먼저 고치고 `CLAUDE.md` 요약을 맞춘다.

## 1. 작업 흐름

```
/issue → /plan → /task → /pr → (다른 사람 PR은) /review → 디렉터가 merge
```

| 스킬 | 하는 일 | 하지 않는 일 |
| --- | --- | --- |
| `/issue` | GitHub 이슈 등록 → `develop`에서 작업 브랜치 생성 → 빈 기획 파일 커밋·푸시 → 이슈에 링크 | 기획 내용 작성, 코드 수정 |
| `/plan N` | 빈 기획 파일을 채움 (목적·규칙·수용 기준·영향 범위). 정한 결정은 `decisions.md`에 기록. 너무 크면 이슈 나누기 제안 | 코드 수정, 이슈·브랜치 생성 |
| `/task N` | 기획 파일대로 조사 → (테스트) → 구현 → 검증 → 문서·기획 파일 갱신 | 커밋·푸시·PR |
| `/pr` | 한국어 커밋 → 검증 통과 후 푸시 → `develop`으로 PR | merge |
| `/review N` | 다른 사람의 PR을 임시 worktree에서 검증하고 리뷰. 확인받은 뒤 승인 또는 댓글 | 코드 수정, merge |
| `/briefing` | 새 세션 시작 시 저장소·GitHub·서버·주기 작업·문서 상태를 점검하고 다음 작업 추천 | 파일 수정, 커밋, 서버 조작 |

새 세션은 `/briefing`으로 시작한다. 상세 문서는 각 스킬이 필요할 때 읽는다.

스킬 정의: `.claude/skills/<이름>/SKILL.md`

### 핵심 원칙
1. **스킬마다 범위가 정해져 있다.** 각 스킬의 `HARD-GATE`(절대 하지 않는 일)를 지키고, 끝나면 다음 스킬을 자동으로 시작하지 않는다.
2. **기획은 파일로 남긴다.** 이슈 본문은 짧게, 자세한 기획은 `docs/plan/<번호>-<설명>.md`. 기획 파일은 코드와 같은 PR로 `develop`에 들어간다.
3. **사람이 결정권자(디렉터)다.** Claude는 제안하고 확정하지 않는다. 커밋·푸시·이슈 생성은 초안을 보여주고 승인받은 뒤에만.
4. **확인하지 못한 것은 못 했다고 쓴다.** 보고와 PR 본문에 "확인한 것 / 확인하지 못한 것"을 나눠 적는다.
5. **로컬 검증이 기준이다.** 검증이 통과해야만 푸시한다. CI(GitHub Actions)는 PR에서 한 번 더 확인하는 보조다.
6. **공개 저장소다.** 호스트 정보와 비밀값은 어떤 공개 산출물에도 남기지 않는다.

## 2. 역할과 결정
- 사용자는 디렉터(결정권자), Claude는 개발 파트너. 제안은 하되 확정하지 않는다.
- 사소하고 되돌리기 쉬운 구현은 판단해서 진행하고 보고에 "임의로 정한 부분"으로 적는다.
- 방향이 갈리는 결정은 선택지와 추천안을 제시하고 디렉터가 고른다.
- 외부 비용·계정·결제가 생기는 일(도메인, 유료 서비스, 외부 백업 저장소)은 반드시 먼저 확인한다.
- `docs/design`의 [미정] 사항은 임의로 확정하지 않는다.

### 승인 없이 하지 않는 일
| 일 | 이유 | 방식 |
| --- | --- | --- |
| sudo 명령 | 호스트 전체에 영향 | Claude는 명령만 제시, 디렉터가 실행 |
| sshd·ufw·NetworkManager·logind 변경 | 원격 접속이 끊길 수 있음 | 명령과 되돌리는 방법을 보여주고 승인. logind는 재시작 금지(재부팅으로 적용) |
| `docker compose down -v`, `data/`·백업 삭제 | 월드 데이터 손실 | 승인 후 실행 |

## 3. 소통
- 한국어 존댓말, 짧고 직접적으로. 확실하지 않으면 추측하지 말고 확인 명령을 먼저 제시한다.
- 문서 표시: [확정] 정해짐 / [임시] 일단 이렇게, 바뀔 수 있음 / [미정] 디렉터 결정 필요 / [아이디어] 아직 할지 모름
- 이모지 사용 금지: 답변, 문서, 코드·주석, 로그 메시지, 이슈, PR, 커밋 메시지 어디에도 쓰지 않는다.
- 보고 형식: 바꾼 것, 확인한 방법, 확인하지 못한 것, 임의로 정한 부분, 커밋·푸시 여부.

## 4. 코드 규칙

### 공개 저장소
- `CLAUDE.local.md`(gitignore)에 호스트 IP, 네트워크 인터페이스, 보안 설정, 실제 외부 포트가 있다.
- 이 값들과 비밀값을 코드·문서·이슈·PR·커밋 메시지에 쓰지 않는다. 필요하면 "`CLAUDE.local.md` 참고" 또는 `.env` 키 이름으로 적는다.

### 비밀값과 설정
- 비밀값(DuckDNS 토큰, RCON 비밀번호, 웹후크 등)과 호스트별 값은 `.env`에 둔다.
- 저장소에는 키 이름과 설명만 적은 `.env.example`을 둔다. 새 키를 추가하면 같이 갱신한다.
- 서버 설정은 `data/` 안 파일을 직접 고치지 않고 `compose.yaml` 환경변수로 관리한다.

### 포트
- Docker로 publish한 포트는 ufw를 우회한다.
- 외부 공개는 마크 서버 포트 하나만.
- 그 외 서비스는 `127.0.0.1:포트:포트` 또는 Tailscale IP로 바인딩.
- RCON(25575)은 절대 `ports`에 넣지 않는다.

### 셸 스크립트
- `#!/usr/bin/env bash` + `set -euo pipefail`
- 여러 번 실행해도 결과가 같게(멱등)
- 실패하면 0이 아닌 종료 코드, 무엇이 실패했는지 메시지 출력
- 주기 실행은 `flock`으로 중복 실행 방지
- 변수는 따옴표로 감싸고, 삭제 경로는 고정 디렉토리 안으로 제한
- 비밀값이 출력에 찍히지 않게 (`set -x` 금지, 토큰이 든 URL 출력 금지)

### 그 밖에
- 식별자·파일 이름은 영어, 주석·문서·로그 메시지는 한국어 가능.
- 과한 도구·라이브러리를 먼저 들이지 않는다.

## 5. 검증
| 대상 | 명령 |
| --- | --- |
| compose | `docker compose config -q` |
| 셸 스크립트 | `shellcheck scripts/*.sh` |
| 관리 API (생긴 뒤) | `pytest` |
| 규칙 | `docs/design/verification.md`의 V1~V14 |

- 해당 파일이 있으면 모두 통과해야 한다.
- 도구가 없어서 못 돌렸으면 통과가 아니다. 멈추고 설치 명령을 제시한다.
- 서버 반영이 필요한 변경(기동, 포트, 접속, 백업 복구)은 직접 확인 목록을 만들고, 못 했으면 못 했다고 적는다.
- CI: `.github/workflows/check.yml`이 develop·main 대상 PR, develop·main push, 수동 실행 때 위 명령과 한 줄 규칙(V1·V2·V3·V5·V7, V4 홈 경로)을 돌린다. `compose.yaml` 필수 변수는 더미 값으로 넣는다.
  - 보조다. 로컬 검증을 대신하지 않고, 브랜치 보호로 merge를 막지 않는다. 결과는 `gh pr checks <번호>`.
  - `CLAUDE.local.md`의 공개 파일 점검 문자열은 CI에 넣지 않는다 (공개됨). 로컬에서만 검사한다.

## 6. 문서
- `docs/design/`은 서버가 "어떻게 동작해야 하는지"의 기준이다.
  - `00-overview.md` 목적, 구성, 디렉토리, 로드맵
  - `systems/` 영역별 문서 (영역 라벨과 1:1)
  - `decisions.md` 결정 기록
  - `verification.md` 항상 지켜야 할 규칙
- 기능을 바꾸면 같은 작업에서 `systems/` 문서를 고친다. 친구에게 영향이 있으면 `docs/player-guide.md`도.
- 방향이 바뀌면 `decisions.md` 표 맨 위에 `| 날짜 | 결정 | 이유 | [#12 기획](../plan/12-....md) |`를 추가하고, 기획 파일 "이 기획에서 내린 결정"에도 적는다.

## 8. Git
- 브랜치: `main`(안정·운영) ← `develop`(통합) ← 작업 브랜치 `<접두어><이슈번호>-<영어-소문자-설명>`
- `main`과 `develop`에 직접 커밋하지 않는다. 작업 브랜치는 최신 `origin/develop`에서 만들고 PR은 `develop`으로.
- 커밋과 푸시는 각각 디렉터가 요청할 때만. (`/pr` 호출, `/issue` 새 이슈 확인, `/plan` 승인은 그 요청에 해당)
- PR merge(**Create a merge commit**)와 `develop` → `main` 반영은 디렉터가 한다.
- 커밋 메시지
  ```
  <태그>: <요약>

  - 변경 1
  - 변경 2

  Co-Authored-By: ...
  ```
  - 태그: `feat` `fix` `hotfix` `ui` `refactor` `test` `docs` `chore` (커밋마다 1개)
  - 메시지는 파일로 넘긴다: `git commit -F <파일>`
- 푸시한 커밋은 고쳐 쓰지 않는다(`--amend`, 강제 푸시 금지).
- 커밋 금지: `.env`, `CLAUDE.local.md`, `data/`, `backups/`, 백업 압축 파일, `whitelist.json`, `ops.json`, 로그.
- 예외: 저장소 초기 설정(스킬 시스템 도입) 커밋은 `develop`을 만들기 전에 `main`에 직접 한다.

## 9. 기획 파일
- 틀과 빈 기획 파일 형태: `docs/plan/README.md`
- 이슈 하나 = 끝나면 실제로 써볼 수 있는 단계 하나. 파일 10개 또는 300줄을 넘을 것 같으면 나눈다.

## 10. 운영 기록 (Notion)
- 운영 기록은 Notion `프로젝트 / minecraft-devops` 아래에 쓴다. 실제 값(인터페이스, 주소, 방화벽 규칙)이 들어가므로 공개 저장소에 두지 않는다. 페이지 주소는 `CLAUDE.local.md`.
- 저장소 `docs/`는 공개용 기준 문서(어떻게 동작해야 하는가), Notion은 운영 기록(실제로 무엇을 했고 무엇이 있었는가)이다.
- 기록 시점: 문제 해결, 설정 변경, 새로 알게 된 것이 있을 때. "정리해"라고 하면 세션 전체를 정리한다.
- 학습 기록: 이 프로젝트는 Docker·DevOps 공부가 목적이다. `/task`가 끝날 때마다 작업 회고와 개념 정리를 쓴다 (아래 형식). 작업 회고는 feature·bug 이슈는 필수, docs·chore는 새로 배운 게 있을 때만.
- 페이지 역할: 지식 노트 = 명령어 치트시트, 원본 로그 = 날짜별 명령·출력, 트러블슈팅 = 문제 1개, 개념 정리 = 원리, 작업 회고 = 이슈 1개의 목표·결정·과정·배운 점. 서로 링크한다.
- 공통: 한국어, 짧게, 이모지 금지. 출력은 핵심 줄만 코드 블록으로. 기존 내용은 지우거나 다시 쓰지 말고 필요한 부분만 수정·추가.

### 현재 구성
- 서버 현재 상태 한 페이지. 바뀐 부분만 수정
- 항목: 하드웨어·OS / 네트워크(인터페이스, 주소) / 원격 접속 / 방화벽 규칙 / 운영 설정(파일 경로) / 서비스 구성 / 남은 할 일

### 트러블슈팅 (문제 1개 = 하위 페이지 1개)
- 맨 위 한 줄: `원인: … / 해결: … (날짜)`
- 증상: 무엇이 안 됐는지 + 핵심 출력
- 가설과 확인:

  | # | 가설 | 확인 방법 | 결과 |
  | --- | --- | --- | --- |

- 원인: 확인한 것만. 확인 못 한 건 "미확인"
- 해결: 실행한 명령
- 배운 점: 1~3줄

### 지식 노트 (카테고리별 하위 페이지에 계속 덧붙임)
- 카테고리: 네트워크 / SSH·원격 접속·보안 / 리눅스 시스템 / Docker (없으면 추가)
- 형식: `명령어` + 한 줄 설명
- 끝에 관련 트러블슈팅 페이지 링크

### 원본 로그 (날짜별 하위 페이지)
- 제목: `N일차 (YYYY-MM-DD)`
- 그날 실행한 명령과 핵심 출력 위주, 해석은 짧게

### 개념 정리 (주제 1개 = 하위 페이지 1개)
- 제목: 주제 이름. 이미 있는 주제면 새로 만들지 않고 덧붙인다
- 맨 위 한 줄: `요약: …`
- 왜 필요한가: 어떤 문제를 푸는지
- 어떻게 동작하나: 흐름도(텍스트 그림 또는 mermaid) + 설명
- 이 프로젝트에서는: 실제 설정·명령 예시
- 헷갈리기 쉬운 점
- 더 볼 것: 공식 문서 링크
- 관련: 작업 회고, 트러블슈팅, 지식 노트 링크

### 작업 회고 (이슈 1개 = 하위 페이지 1개)
- 제목: `#N <이슈 제목>`
- 맨 위 한 줄: `결과: … (날짜, PR #)`
- 목표
- 결정과 이유:

  | 결정 | 고른 것 | 다른 선택지 | 이유 |
  | --- | --- | --- | --- |

- 과정: 단계별 핵심 명령. 자세한 출력은 원본 로그 링크
- 막힌 것: 트러블슈팅 링크 (없으면 "없음")
- 배운 점: 1~5줄 + 개념 정리 링크
- 다음에 할 것
